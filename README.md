# vps-troubleshooting

VPS 变慢、连不上、或者网站能打开却登不进去时，交给 AI 按一套固定流程排查：先测量，再判断问题在服务器、在跨境线路、还是在你自己这边，最后才决定要不要改。

适用于任何 VPS、任何服务商。换机房、换线路，方法都一样。

**你不需要懂 Linux、不需要懂网络。** 你只要会说清楚症状。

## 怎么用

把下面这句话发给任意一个能读网页或文件的 AI（Claude Code、Codex、Cursor、pi 都可以）：

```
读 https://github.com/Vist233/vps-troubleshooting 里的 skill/vps-troubleshooting/SKILL.md，
按它的流程诊断我这台 VPS，先只做只读检查。
```

AI 会先做**只读检查**，不碰任何配置。要改动之前会先把方案和回滚方式讲给你，由你决定。

如果你自己会用命令行，也可以直接读 `skill/vps-troubleshooting/references/` 下对应的文件，里面有命令和判断标准。

## 它会怎么查

不用你懂，但你可以知道它在做什么：

1. **只读采集**——系统、端口、内核参数、网卡错误、失败的服务，只看不改
2. **分层测量**——先测服务器自己有多快，再测单条连接、多条连接，把问题钉到某一层
3. **对照实验**——改一个东西前，先交替测"改"和"不改"两组，而不是凭感觉
4. **给选项**——告诉你几种做法分别能改善什么、不能改善什么
5. **你决定**——改动、回滚、或者什么都不做

### 症状对应哪一路

| 你遇到的情况 | 先查什么 | 详细步骤 |
| --- | --- | --- |
| 新机器，还没配 | 系统、架构、已占端口，再定传输方式 | [deploy](skill/vps-troubleshooting/references/deploy.md) |
| 能用，但慢 | 先测 VPS 自身速度，排除服务器问题 | [slow-path](skill/vps-troubleshooting/references/slow-path.md) |
| 连接超时或被重置 | 查两层防火墙，再查路径 | [unreachable](skill/vps-troubleshooting/references/unreachable.md) |
| 网站能开但登录失败 | 先看出口 IP 有没有变，再看是哪类拒绝 | [login-blocked](skill/vps-troubleshooting/references/login-blocked.md) |
| 多设备，订阅拉不下来 | 确认是下载失败还是解析失败 | [multi-device](skill/vps-troubleshooting/references/multi-device.md) |

## 实测

一台洛杉矶 VPS，客户端在北京走移动网络。三步排查的全部数据：

| 步骤 | 测量 | 结果 | 说明 |
| --- | --- | ---: | --- |
| 1 定位层次 | VPS 到公网下载 | 约 45 MB/s | 服务器上行不是瓶颈 |
| 1 定位层次 | 单条连接下载 | 14–15 KB/s | 比服务器慢三个数量级 |
| 1 定位层次 | 四条并行合计 | 51.5 KB/s | 容量存在，单条被压制 |
| 1 定位层次 | 延迟 RTT | 约 195 ms | 路径长，窗口涨得慢 |
| 1 定位层次 | 丢包 | 6.7%–20% | 间歇丢包打垮基于丢包的算法 |
| 1 定位层次 | 传输中窗口 cwnd | 1–3 MSS | 窗口塌了 |
| 1 定位层次 | 重传比例 | 约 15.7% | 是真丢包，不只是延迟 |
| 2 改拥塞控制 | CUBIC（三轮中位数） | 34.0 KB/s | 对照组 |
| 2 改拥塞控制 | BBR（三轮中位数） | 108.6 KB/s | 约 3.19 倍，但仍不快 |
| 3 换入口 | 原节点直连 | 1.075 MB/s | 对照组，Shadowsocks |
| 3 换入口 | 新方案经 Cloudflare | 1.592 MB/s | 比原节点高约 48% |
| 3 换入口 | 同协议直连源站 | 1.347 MB/s | 比同协议直连高约 18% |

第 2、3 步都是交替三轮。BBR 的六次读数：CUBIC 34.0 / 29.8 / 42.4，BBR 110.9 / 104.2 / 108.6；两步的三轮区间都互相重叠，所以给的是中位数和量级，不是固定倍数。

**关键证据是第 1 步里单条和并行的差距**：四条加起来 51.5 KB/s，单条只有 15 KB/s，说明链路还有余量，问题出在单条连接的拥塞控制，不在带宽。

同一份表也说明了测量的另一半作用：BBR 确实把速度提到 3 倍，**但 108 KB/s 仍然不快**，证明这台机器不适合当主力出口。改动有效，和不值得继续投入，可以同时成立。

## 常见问题

### 我完全不懂技术，能用吗

能。你只需要描述症状，比如"晚上特别卡""打开网页转圈但微信正常"。AI 负责执行和判断，你负责决定要不要改。

### 它会不会把我机器搞坏

默认只读。采集和测量都不改任何配置。真要改动时，流程要求先给出回滚办法，并且只改一项、立刻复测。

### 这个和别的 AI Skill 有什么区别

多数 VPS 类工具直接给你一套"优化参数"或一个一键脚本，改完重启，快不快靠感觉。

这个仓库的差别是**先测量、再决定改不改**：

- 判断有证据门槛。测速必须交替对照、每组至少 3 个样本；如果你只跑一次就得出"提升 3 倍"，脚本会拒绝出结论
- 明确写了做不到什么。CDN 改变入口但不改出口 IP；BBR 改善发送侧但不创造容量
- 讲清边界而不是给承诺。不推荐厂商、不分享节点、不做协议排名

如果你要的就是一条命令搞定，这个仓库不是那种东西。

### 能不能直接抄一套网上推荐的参数

不建议。缓冲区大小取决于带宽乘延迟、内存、并发数和这台机器的角色。1 GB 内存的机器抄 256 MB 缓冲，只会变成负担。

## 不做什么

- 不推荐 VPS 厂商，不分享节点，不做协议排名
- 不提供 `curl | sh` 一键安装脚本
- 不承诺任何出口能通过第三方风控
- 不把"能用"当成"安全"

## 结构

```
skill/vps-troubleshooting/SKILL.md      给 AI 的入口：路由、证据顺序、判断规则
skill/vps-troubleshooting/references/   五个分支，含命令和判断标准
skill/vps-troubleshooting/scripts/inspect.sh   只读采集主机状态
skill/vps-troubleshooting/scripts/measure.py   交替对照测速，会拒绝不平衡样本
```

`scripts/` 是给 AI 执行的，你不用手动跑。

`SKILL.md` 保持简短，只在需要时加载对应分支。
