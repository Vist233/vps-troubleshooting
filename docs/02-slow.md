# 2. 慢：先定位，再调

"慢"不是诊断结论。它至少是五种完全不同的故障，用户感觉起来一样。按成本从低到高逐项排除。

## 判断树

```
用户说：慢
  │
  ├─ VPS 自己快不快？            → 从 VPS 直接测到公网
  │    不快 → 服务器上行 / 服务商 / 硬件问题
  │    快 ↓
  │
  ├─ 单流慢，但多流加起来正常？
  │    是 → 拥塞控制 / 路径丢包        ← 调优可能有效
  │    否 ↓
  │
  ├─ 全天都慢吗？
  │    不是 → 高峰期限速，调优解决不了容量
  │    是 ↓
  │
  └─ 是不是客户端自己的网络到头了？   → 换个网络重测
```

按这个顺序测，每一步都可能直接结案。

## 第一步：服务器自己快不快

从 VPS 测到附近、连接良好的目标，**不要测到用户**。

```bash
curl -o /dev/null -w '%{speed_download} B/s\n' \
  'https://speed.cloudflare.com/__down?bytes=10000000'
```

顺便看网卡错误和丢包：

```bash
ip -s link show
```

**怎么读：** 几十 MB/s 且 errors/drops 为 0，说明服务器上行不是瓶颈。用户看到的低速度发生在**路径上**，不在机器上。

这一步能排除最常见的错误猜测——"VPS 太弱 / 服务商超售"。

## 第二步：单流 vs 多流

整个流程里信息量最大的一次测量。

同一个文件下载两次：一次单流，一次 N 条并行。

- **单流 ≈ 多流总量 / N** → 链路有容量，是单条流被压制。拥塞控制、丢包或限速。
- **单流 ≈ 多流总量** → 路径本身被限死。加并发没用，调优也没用。

第一种情况的例子：单流约 15 KB/s，四条并行合计约 51 KB/s。**容量是存在的，是一条流被惩罚了。**

两个数字都要记。只报单流数字，会把人引向错误的修法。

## 第三步：测真实路径的 RTT 和丢包

```bash
ping -c 30 <vps>
mtr -rwzc 30 <vps>     # 如果有
```

看三件事：

- **RTT**：决定带宽时延积有多大。约 195 ms 意味着长路径，窗口增长很慢。
- **丢包**：5%–20% 的间歇丢包会打垮基于丢包的拥塞算法。这是长路径上单流速度极低的最常见原因。
- **丢包从哪一跳开始**：`mtr` 能看到。只在最后一跳出现丢包，往往是 ICMP 限速而不是真丢包——要用 TCP 侧证据确认。

跨境家宽线路同时出现高 RTT 和间歇丢包很常见。这是路径属性，不是配置错误。

## 第四步：用 TCP 状态确认，而不是只看吞吐

光看吞吐分不清"路径差"和"服务器配错"。传输过程中在 VPS 上采样真实连接：

```bash
ss -tin dst <客户端IP>
```

读这些字段：

| 字段 | 小/大意味着什么 |
| --- | --- |
| `cwnd` | 传输中只有 1–3 MSS，说明窗口塌了——丢包或限速 |
| `ssthresh` | 掉到 2，说明反复发生丢包事件 |
| `retrans` / `bytes_retrans` | 比例高（如约 15%）确认真实丢包，不只是延迟 |
| `rtt` | 和 ping 一致吗？不一致说明有东西在中间拦截 |
| delivery rate | 服务器上行正常但它极低 → 路径问题 |

这一步把"感觉慢"变成"在 195 ms 路径上，窗口塌到 1–3 MSS，重传率约 15%"。**后者可操作，前者不可操作。**

## 确认是路径问题后，按证据强弱依次尝试

### A. 改发送端的拥塞控制

在有丢包的长 RTT 路径上，基于丢包的算法（CUBIC）会反复塌窗。BBR 用建模代替丢包判断，对丢包更宽容。

**不要直接改全局设置**，否则机器上其他所有连接都跟着变。优先在独立测试连接上用 `TCP_CONGESTION` 按 socket 设算法，全局保持原样。

对照方法：

- 交替顺序 `CUBIC, BBR, BBR, CUBIC, CUBIC, BBR`，抵消时段漂移；
- 报多轮的中位数，不报最好那一轮；
- 注意上传常常没变化——服务器的算法管不到客户端的发送方向。

在差线路上，现实结果是提升几倍但仍然不快。**照实说，不要宣布胜利。**

**BBR 不能创造容量。** 如果第二步测出单流 ≈ 多流，BBR 不会变出带宽。

### B. 在入口前面加 CDN

如果问题在"客户端→VPS"这一段，改变客户端**怎么**到达 VPS 可能有帮助，因为客户端改为连附近的边缘节点，不再直接穿过那条差路径。

前提是 HTTP 系传输（见 [01-deploy.md](01-deploy.md) 1.2）。裸 Shadowsocks 加不了。

现实预期：幅度有限且不稳定。实测过的一个案例里，CDN 路径比原节点高约 48%、比同协议不加 CDN 高约 18%，但多轮区间互相重叠，有时候更慢。**不要承诺固定倍数。**

它**不**做什么：出口 IP 不变，所以第三方风控的判断不变（见 [04-login-blocked.md](04-login-blocked.md)）。

### C. 换网络或换区域

如果第一到四步都指向路径差、而调优收益很小，诚实的建议是换运营商或换机房。**不要继续调一条没有容量的路径。**

即使这不是用户想听的答案，只要证据支持就要说。

## 反面做法

不要做这些；被问起时说明原因：

- **从博客抄一段 sysctl。** 缓冲区大小取决于带宽、RTT、内存、并发和机器角色。1 GB 内存的机器上设 256 MB 缓冲是负担，不是优化。
- **因为"一般都是 1440"就改 MTU。** 先探测 PMTU；MTU 错了会导致某些路径静默卡死。
- **一看到重传就限速。** 重传是症状，限速是叠加第二个问题。
- **全局开 BBR 就算完成。** 它影响机器上每一条连接，包括你没打算改的服务。
- **只报最好的一轮。** 报中位数，并说明跑了几轮。
